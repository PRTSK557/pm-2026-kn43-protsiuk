# Вибір підходу для трьох проєктів та власна тема

## 1. Зведена таблиця рішень

| Кейс | Обраний підхід | Критерій конфлікту | Ціна вибору |
| --- | --- | --- | --- |
| C-1 | predictive | technology | Гнучкістю та швидкістю реагування на сире API реєстру заради дотримання жорсткого fixed price контракту |
| C-2 | adaptive | release_cost | Стабільністю грошових розрахунків на старті заради максимальної швидкості перевірки продуктових гіпотез |
| C-3 | hybrid | requirements | Часом і ресурсами на гнучке узгодження винятків заради безпеки перенесення критичних фінансових даних |

---

## 2. Кейс C-1. Модуль звітності до державного реєстру

- **Конфлікт критеріїв:** Ключовим протиріччям є зіткнення стабільних нормативних вимог (`requirements` тягне в predictive) та сирого, нестабільного API реєстру (`technology` тягне в adaptive). Оскільки контракт є суворим fixed price з юридичними штрафами за зрив строків, ми обираємо предиктивний підхід.
- **Що робимо з критерієм проти:** Закладаємо додатковий резерв часу в графік на можливі зміни протоколів API та вимагаємо від підрядника ранньої фіксації інтеграційних контрактів.
- **Відкинутий підхід (Adaptive):** Плюс — можливість гнучко адаптуватися під зміни методів держреєстру; мінус — неможливість контролювати бюджет і строки перед замовником за умовами тендеру.
- **Перший тиждень:** Проведення спільної технічної наради з підрядником щодо аналізу документації API реєстру, узгодження формату пакетів звітів та підписання стартового технічного протоколу.

---

## 3. Кейс C-2. Платіжна частина сервісу оренди обладнання

- **Конфлікт критеріїв:** Головний конфлікт полягає між мінливими бізнес-гіпотезами (`requirements` тягне в adaptive) та високою ціною помилки у фінансових розрахунках (`release_cost` тягне в predictive). Обрано адаптивний підхід через наявність внутрішнього продукту і залученого засновника.
- **Що робимо з критерієм проти:** Виділяємо платіжну логіку в ізольований модуль і покриваємо критичні фінансові операції автоматичними тестами перед кожним релізом.
- **Відкинутий підхід (Predictive):** Плюс — суворий контроль та ретельна перевірка кожної фінансової формули; мінус — втрата часу на бюрократію, через що стартап втратить конкурентність на ринку.
- **Перший тиждень:** Налаштування автоматизованого середовища розгортання, створення ізольованого контуру для роботи з тестовим еквайрингом та проведення першого інтерв'ю з користувачами щодо розрахунку застав.

## 4. Кейс C-3. Заміна внутрішньої системи обліку договорів

- **Конфлікт критеріїв:** Зіштовхуються заплутані й неповні реальні бізнес-вимоги (`requirements` тягне в adaptive) та жорсткі рамки річного fixed price бюджету й бухгалтерії (`contract` і `release_cost` тягнуть в predictive). Обрано гібридний підхід.
- **Що робимо з критерієм проти:** Ядро системи (реєстр і щомісячні нарахування) реалізуємо предиктивно за чітким планом, а інтерфейси погоджень та винятки розробляємо ітеративними хвилями.
- **Відкинутий підхід (Pure Adaptive):** Плюс — повна гнучкість до всіх винятків юридичного відділу; мінус — вихід за межі річного бюджету наглядової ради через відсутність чіткого фінішу.
- **Перший тиждень:** Запуск повного аудиту якості наявних даних у старій системі договорів, виявлення розривів у контрагентах і затвердження базової архітектури майбутнього реєстру.

## 5. Стрес-тест контрактом (Конверт C-1)

- **Рішення до конверта:** Обирали предиктивний підхід через жорсткий fixed price контракт і суворі вимоги регулятора. Головним конфліктом виступала сира технологія (API).
- **Рішення після конверта (зміна на Time and Material):** Підхід залишається предиктивним за своєю структурою контролю, але суттєво змінюється модель взаємодії: ризик невизначеності API повністю знімається з виконавця і переходить на замовника. PM більше не боїться змін методів реєстру, оскільки кожна година додаткового опрацювання оплачується. У роботі PM з'являється щомісячне узгодження фактично відпрацьованих годин замість закриття великих етапів за актами.
- **Два робочі ходи PM для фіксованої ціни при мінливих вимогах:**
  1. *Формалізація через межі зміни (Change Request Budget):* Закладка в контракт фіксованого буфера на коригування вимог із погодинною тарифікацією понад базовий обсяг. Ціна ходу: складні переговори з юристами замовника на старті тендеру.
  2. *Метод витіснення функціоналу (Trade-off Matrix):* Фіксація бюджету та строків із умовою, що поява нових вимог автоматично витісняє старі еквівалентні за трудомісткістю функції з першого релізу. Ціна ходу: ризик невдоволення стейкхолдерів скороченням обсягу.

## 6. Власний проєкт: «Платформа обліку практик і стажувань»

- **Тема:** Платформа обліку практик і стажувань: студент, база практики, керівник, звіти.
- **Обраний підхід:** Гібридний (Hybrid). Предиктивний каркас для звітів перед університетом та базової структури ролей, адаптивні ітерації для інтерфейсів студентів і баз практики.
- **Чому саме так:** Враховуючи команду варіанта V10 (PM 50%, BA 25%, розробники 100%, QA 50%, DevOps 50%), обмежений строк у 14 тижнів та помірну доступність замовника, чистий адаптивний підхід призведе до хаосу в інтеграціях звітів, а чистий предиктивний — зупинить розробку при уточненні вимог баз практики. Ситуація відрізняється від кейсів тим, що є чіткий ліміт часу (14 тижнів) і неповна ставка BA з QA, що вимагає жорсткої приорітизації.
- **Зв'язок із ризиком ЛР1:** Враховує Ризик №3 з ЛР1 (недостатність повної ставки QA та DevOps для навантажувального тестування пікового завантаження звітів наприкінці семестру), тому гібридний план передбачає раннє створення інтеграційного тестового контуру.

### Операційне середовище проєкту:
- **Довжина ітерації:** 2 тижні.
- **Події:** Щопонеділка — планування спринту (30 хв), щоп'ятниці — демо та ретроспектива (30 хв), щодня — асинхронний стендап у чаті.
- **Дошка і WIP:** Kanban-дошка в GitHub Projects; ліміти WIP: для в розробці (In Progress) — не більше 3 задач на команду, для тестування (In QA) — не більше 2 задач.
- **Definition of Done (DoD):** 
  1. Код пройшов Code Review та злитий у гілку `main`.
  2. Написані модульні тести для бізнес-логіки.
  3. Функціонал перевірений на стейджі та відповідає критеріям прийняття (Acceptance Criteria).
- **Точка приймання:** Підписання демо-акту керівником академічної практики або викладачем наприкінці двотижневого спринту.
